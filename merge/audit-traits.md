# Traits editor — what the reference tool has, and what we took

_Phase 8. Compared against `refs/upstream/editor/main` at the SHA in
`merge/SYNC_LOG.md`: `src/components/traits/{TraitsParser,TraitEditor,TraitList,
TraitsContext,TraitsFileLoader}.jsx` and `src/pages/TraitsEditor.jsx`._

**Verdict: their field list is complete and we match it exactly. Their file
handling is not safe to port, and their trigger half does not exist.**

## Field coverage

Every field their editor exposes, ours does too. Nothing in this table is missing
on our side, so the roadmap's "matched or exceeded" is a match on fields and an
exceed on everything around them.

| Field | Theirs | Ours |
|---|---|---|
| `Trait <name>` | ✅ editable | ✅ editable (new traits only — see below) |
| `Characters` | ✅ comma list | ✅ single picker + the engine bug named |
| `Hidden` | ✅ | ✅ |
| `ExcludeCultures` | ✅ | ✅ |
| `NoGoingBackLevel` | ✅ | ✅ |
| `AntiTraits` | ✅ | ✅, with the mod's own trait names offered |
| `Level <name>` | ✅ add / delete | ✅ add / delete |
| `Description` / `EffectsDescription` | ✅ key + text | ✅ key + text |
| `GainMessage` / `LoseMessage` / `Epithet` | ✅ key + text | ✅ key + text |
| `Threshold` | ✅ | ✅ |

| trait add / delete | ✅ | ✅, and the orphaned triggers go with it |

## What we took from them

**Editing the displayed text beside its key.** Their level rows put the
`export_VnVs.txt` wording next to the key that names it, so writing a trait and
writing what it says are one job. That is plainly right and we had not planned
it — our first cut showed the text read-only and wrote placeholders. Adopted:
`traits.plan(…, loc={tag: text})`, upserted into the `.txt` (or straight into the
compiled archive for a mod that ships no `.txt`) and recompiled in the same save.

**A key with no entry is worth shouting about.** They disable the box and say
"No description key". We go further because the guide is explicit that it is a
CTD, not a blank: the trait names the missing keys at the top of the pane, and a
save creates them with the key as placeholder text rather than leaving the crash.

## What we did not take, and why

**Their serializer, which rewrites the whole file.** `serializeTraitsFile` emits
the file from the parsed model: every comment banner in the mod is replaced with
their own, `_comments` is collected per trait and never written back, and the
first two lines become "generated by Mylae's M2TW Mod Editor". Saving one trait
reformats all 36 000 lines of DaC's EDCT. Ours splices — an untouched line keeps
its bytes, and all 1457 real traits re-render to themselves unchanged
(`tests/test_traits.py`). This is the same ruling every editor in this toolkit
has made, and the reason `parse_text(t).text() == t` is the phase's gate.

Three data losses fall out of that serializer specifically:

* a level with no `Threshold` line parses as `threshold: 0` and is written back
  as `Threshold  0`, below the hardcoded minimum of 1;
* `Affects X 1 chance 100` is written lower-case, where every one of the 5523
  `Affects` lines in the installed mods writes `Chance`;
* comments, blank-line grouping and the mod's own indentation are gone.

**`parseTextFile`'s wide-char handling.** It reads UTF-16 as if it were bytes and
tries to detect "every other character is a space" to undo it — and
`collapseWideChar` returns before its own second `return`, so it does nothing
anyway. There is no need for any of it: `export_VnVs.txt` is UTF-16 and we read
it as UTF-16, falling back to the compiled `.strings.bin` through Phase 6's codec
when a mod ships no `.txt` (their loader cannot open such a mod at all).

**Their trigger half.** `parseTrigger` keeps each condition as a raw string
(`trigger.conditions.push(line)`), so there is no vocabulary, no operand pickers
and no way to know whether a condition can ever be true. Ours is `triggers.py`
plus `web/js/triggerui.js` — 413 conditions and 217 events of generated
vocabulary, typed boxes per argument, and the never-fires warning. See
`merge/audit-trigger-vocab.md` for why their `conditionDefs.jsx` could not be
used as its source.

## What we have that they do not

* **Checks.** `traits.check_file` reads both halves of the file together: header
  lines in an order the engine will not accept, a level whose threshold a lower
  level already reached (so it can never appear), an `AntiTraits` naming a trait
  that does not exist, an `Affects` naming one, a comma-separated `Characters`
  list where only the first entry works. 14 real findings across the three
  installed mods, including a trait in DaC that lost its `Trait` line and has
  been silently absorbed as an unreachable level of its neighbour.
* **Code View.** The trait's own text beside the boxes, hover-linked line by line,
  both directions live — and a hand edit reaching disk verbatim.
* **Backups and undo** on every write, covering the EDCT, `export_VnVs.txt` and
  its compiled archive as one job.
* **Localised names in the list**, per the toolkit's rule: "Ring-bearer
  (OneRingAddiction)".

## Deliberately deferred

Their `Wand2` "Auto" button writes an effects description from the level's
`Effect` lines ("+1 Command, +1 Troop Morale"). It is string templating rather
than an AI feature, so the locked no-autogenerate rule does not forbid it, but it
guesses the mod's house wording and phrasing conventions — worth revisiting with
a mod's existing descriptions as the model rather than a format string.
